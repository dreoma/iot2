# Правила и уведомления

Каждое новое измерение хранит `device_id` и `user_id` владельца на момент
приёма. `user_id` из запроса устройства не используется: ядро находит владельца
через `user_devices`. Для устройства без владельца запись отклоняется (404).
Предыдущее значение выбирается только среди измерений этого же владельца.

Уведомление в Telegram и обе версии Email содержат название и ID устройства,
ID владельца и его почту, ID измерения, ID и условие правила, поле, значения
до/после и время события. В API истории поле `context` хранит неизменяемый снимок:
`occurred_at`, `device`, `user`, `rule`, `telemetry` (включая полные JSON-пакеты).
Переименование устройства или редактирование правила не меняет прошлое событие.

При `docker compose up` сервис `db-migrate` применяет повторяемые SQL-миграции
к существующим базам без удаления данных. Старые измерения имеют `user_id:null`,
старые уведомления — `context:{}`: исторического владельца не восстанавливаем
по текущему состоянию устройства. При запуске без Compose эти же SQL нужно
применить вручную: `db/telemetry_context.sql` к основной БД,
`db/notification_context.sql` к базе правил.
При удалении пользователя внешний ключ измерений `user_id` обнуляется;
снимок владельца в ранее созданных уведомлениях сохраняется.

Правила проверяются в `services/rule_engine.cpp` после сохранения расшифрованной
телеметрии. SQL отделён в `repositories/rule_repository.cpp`, HTTP-маршруты —
в `routes/rule_routes.cpp`. Таблицы `rules` и `notifications` находятся в отдельной
базе PostgreSQL `iot_rules` (контейнер `rules-db`). Основная БД не пересоздаётся.

## Создание правила

Замените `device_id` на идентификатор существующего устройства:

```bash
curl --noproxy '*' --cacert certs/ca.crt --resolve core-tls:8443:127.0.0.1 \
  -X POST https://core-tls:8443/rules \
  -H 'Content-Type: application/json' \
  -d '{"device_id":1,"field":"temperature","operator":"gt","threshold":30,"message":"Температура выше 30 °C","enabled":true}'
```

Владелец правила определяется автоматически по устройству. Параметр `field`
указывает на поле верхнего уровня `data`, например `temperature`, `humidity`,
`door`. Вложенные пути вида `sensor.temperature` не разбираются.

| operator | Условие |
| --- | --- |
| `gt`, `gte` | Значение больше / больше или равно порогу |
| `lt`, `lte` | Значение меньше / меньше или равно порогу |
| `eq`, `ne` | Значение равно / не равно порогу |
| `changed` | Значение изменилось относительно предыдущего измерения; threshold необязателен |
| `delta` | Абсолютная разница с предыдущим значением >= положительного threshold |

Сравнения и `delta` работают с числами. `changed` также подходит для boolean и
строк. Отсутствующее поле или `null` не вызывает уведомление. Предыдущее значение
берётся из непосредственно предыдущего пакета устройства, а не из последнего
пакета, где поле присутствовало.

Для пороговых правил уведомление создаётся только при переходе из ложного
условия в истинное. Пример: 20 → 35 → 36 → 25 → 40 при `gt 30` создаст два
уведомления, на 35 и 40. Первое измерение тоже может вызвать пороговое правило;
`changed` и `delta` требуют предыдущего значения.

## API

Запросы требуют `Authorization: Bearer <token>`. Пользователь управляет правилами
своих устройств и видит собственные уведомления.

- `POST /rules` — создать правило;
- `GET /devices/{id}/rules` — получить правила устройства;
- `PUT /rules/{id}` — полностью заменить настройки (то же тело, что и POST);
- `DELETE /rules/{id}` — удалить правило;
- `GET /users/{id}/notifications` — последние 100 готовых уведомлений пользователя.

Для отключения правила отправьте PUT с `enabled:false`. Если у устройства
`notifications_enabled:false`, уведомления не создаются, но телеметрия продолжает
сохраняться. Проверяются только правила текущего владельца устройства.

Ответ на запись телеметрии содержит `rules_evaluated` и `notifications_created`.
При недоступной rules-db телеметрия сохраняется, а `rules_evaluated:false` сообщает
о пропуске проверки. Автоматической повторной проверки пока нет.

Уведомление содержит `user_id`, `telegram_id`, `device_id`, текст, предыдущее и
новое значения. После сохранения срабатывания rule engine передаёт сообщение
в `NotificationService`, перенесённый из ветки `feature/notifications-semyon`
(`ef27b14`) проекта iot-platform. Фоновый поток отправляет его через все настроенные
каналы `INotifier`: TgBot для Telegram и libcurl/SMTP для Email. Сохранены команды
бота `/start`, `/help`, текстовый и HTML-шаблоны письма. Структура `Notification`
дополнена текстом правила, именем поля и предыдущим/новым значениями.

В отличие от исходного main.cc, здесь создаётся один `NotificationService` с обоими
каналами. Telegram создаётся только при непустом `IOT_TELEGRAM_BOT_TOKEN`.
После подтверждения в личном чате бот привязывает Telegram ID во время регистрации.
Уведомления используют сохранённый `users.telegram_id`. В iot2 нет отдельного
имени пользователя и sensor_id: в сообщениях используются mail и id устройства.

Очередь отправки, как в исходной ветке, находится в памяти. Неуспешная отправка
логируется без повторной попытки, отправленные статусы в БД не отмечаются.
Таблица `notifications` служит историей срабатываний, а не подтверждением доставки.
Старые события автоматически не рассылаются. При резком завершении процесса
неотправленная очередь теряется, но история остаётся.

## Настройка каналов

Добавьте в `.env`:

```dotenv
IOT_TELEGRAM_BOT_TOKEN=токен_от_BotFather
IOT_SMTP_URL=smtp://mailpit:1025
IOT_SMTP_FROM=iot@example.com
IOT_SMTP_USER=
IOT_SMTP_PASSWORD=
```

Письмо отправляется на `users.mail`. Mailpit принимает локальные тестовые письма;
просмотр — http://localhost:8025. Для реальной почты укажите свой SMTP-сервер
(`smtp://host:587` или `smtps://host:465`), логин, пароль и адрес отправителя.
Для отключения Email задайте `IOT_SMTP_URL=`; пустой токен отключает Telegram.
После изменения `.env`: `docker compose up -d --force-recreate iot-core`.

## Запуск и проверка

Используйте [локальный тестовый стенд](../LOCAL_SETUP.md#8-проверить-тестами-без-реальных-рассылок).
Он отправляет запросы Telegram в заглушку и направляет письма в Mailpit.

Тест проверяет CRUD, шифрованную телеметрию, пороговые переходы, `changed`, `delta`,
отключение уведомлений и некорректные правила. Созданные им записи удаляются.
