= Спринт 5. Пароли, соль, перец и сессии
:toc: macro
:toc-title: Содержание

В IoT2 пользователь входит по email и паролю. После входа сервер выдаёт токен
на 24 часа. По этому токену API определяет пользователя и проверяет, какие
устройства, правила и уведомления ему доступны.

toc::[]

== Как проходит регистрация

. Введите email. `POST /auth/register/start` создает попытку и возвращает токен
  регистрации и ссылку на Telegram-бота. Ссылка действует 10 минут.
. Откройте ссылку и нажмите «Старт» в личном чате. Бот получает ID отправителя,
  а сайт проверяет `GET /auth/register/status` с токеном регистрации.
. После подтверждения задайте пароль. `POST /users` принимает поле `password`
  и токен регистрации в заголовке. Ядро сохраняет email и Telegram ID
  из подтверждённой попытки и удаляет её.

В `.env` должен быть настроен `IOT_TELEGRAM_BOT_TOKEN`. Для входа в уже
созданный аккаунт достаточно email и пароля.

== Что происходит с паролем

На последнем шаге регистрации `POST /users` принимает пароль.
Пароль должен занимать от 15 до 256 байт. Email при входе указывают в том же
виде, в каком он записан в профиле.

. Ядро вычисляет HMAC-SHA-256 от пароля. Ключ HMAC — *перец*, общий секрет
  приложения из переменной `IOT_PASSWORD_PEPPER_HEX`.
. Libsodium хеширует результат HMAC алгоритмом Argon2id. Библиотека генерирует
  *соль* отдельно при каждом хешировании и включает её в строку хеша вместе
  с параметрами Argon2id. Поэтому у одинаковых паролей получаются разные хеши.
. Ядро помечает строку префиксом `pepper-v1:` и сохраняет её в
  `iot_core.users.password_hash`. Исходный пароль и перец в PostgreSQL
  не сохраняются.

При входе сервер по email находит сохранённый хеш и передаёт его вместе с
результатом HMAC от введённого пароля в функцию проверки libsodium.
Библиотека извлекает соль и параметры из хеша и проверяет, совпадает ли результат.

Для старых хешей, созданных до добавления перца, сервер сначала проверяет
пароль по прежней схеме. При успешном входе он сохраняет новый хеш с перцем
одновременно с выдачей сессии. Учётным записям с `password_hash IS NULL`
оператор сначала назначает пароль. Порядок описан в
link:iot-core/README.md#пароли-для-существующих-пользователей[инструкции для существующих пользователей].

Для новой установки с пустым `IOT_PASSWORD_PEPPER_HEX` сгенерируйте отдельный
ключ командой `openssl rand -hex 32` и сохраните его в `.env`. Сохраните этот
же ключ при переносе установки и держите резервную копию отдельно от дампа БД.
При потере или замене ключа пользователям с хешами `pepper-v1:` потребуется
заново установить пароли. Ключ телеметрии `TRAFFIC_KEY_HEX` на проверку паролей
не влияет.

== Как работает сессия

. Клиент отправляет email и пароль по HTTPS в `POST /auth/login`. При успехе
  сервер возвращает JSON с полями `token`, `user_id` и `expires_in`.
  Значение `expires_in` равно `86400` секундам.
. Токен состоит из 64 шестнадцатеричных символов, полученных из 32 случайных
  байт. Сервер хранит в `users.session_digest` SHA-256 токена, а в
  `users.session_expires_at` — момент окончания сессии.
. Для каждого защищённого запроса клиент отправляет заголовок
  `Authorization: Bearer <token>`. Фильтр хеширует токен, ищет в БД
  совпадение с неистёкшей сессией и передаёт ID пользователя обработчику.
. У каждого пользователя одна активная сессия. Повторный вход, даже на другом
  клиенте, заменяет предыдущий токен. Обычные запросы срок сессии не продлевают.
  Выход или смена пароля очищают поля сессии. Чтобы получить новый токен,
  снова вызовите `POST /auth/login`.

Храните токен как пароль. Любой, у кого есть действующий токен, может отправлять
запросы от имени пользователя. Передавайте его по HTTPS в заголовке и удаляйте
на стороне клиента после выхода. При `401` на защищённом маршруте проверьте
заголовок и войдите заново, если сессия истекла или была заменена.

== Маршруты API

[cols="2,1,3", options="header"]
|===
|Маршрут |Токен |Результат

|`POST /auth/register/start`
|Нет
|Принимает `mail`. Возвращает ссылку на бота и токен регистрации со статусом `201`.

|`GET /auth/register/status`
|Токен регистрации
|Возвращает `telegram_confirmed`. Для истёкшего токена ответ `404`.

|`POST /users`
|Токен регистрации
|Принимает `password` после подтверждения в Telegram. Возвращает профиль с `id`
и статус `201`. Попытка завершить регистрацию до подтверждения даёт `409`.

|`POST /auth/login`
|Нет
|Принимает `mail` и `password`. Возвращает токен со статусом `200`.
Неверный email или пароль даёт `401`.

|`POST /auth/logout`
|Да
|Завершает текущую сессию. Возвращает `204` без тела.

|`PUT /auth/password`
|Да
|Принимает `current_password` и `new_password`. При успехе возвращает `204`
и завершает сессию. Неверный текущий пароль даёт `403`.

|`GET /users` +
`GET /users/{id}` +
`PUT /users/{id}` +
`DELETE /users/{id}`
|Да
|Работа со своим профилем. `GET /users` возвращает массив с собственным
профилем. Обновление профиля принимает только `mail`. Для смены пароля предусмотрен `PUT /auth/password`.

|`POST /devices` +
`GET /devices` +
`GET /devices/{id}` +
`PUT /devices/{id}` +
`DELETE /devices/{id}`
|Да
|Работа со своими устройствами. В теле запроса на создание передают `name`
и при необходимости `notifications_enabled`. Владелец определяется по сессии.

|`POST /rules` +
`PUT /rules/{id}` +
`DELETE /rules/{id}` +
`GET /devices/{id}/rules` +
`GET /users/{id}/notifications`
|Да
|Управление правилами своих устройств и чтение собственных уведомлений.
|===

Чужой ресурс возвращает `404`. Некорректное тело запроса обычно даёт `400`,
а слишком частые запросы к маршрутам работы с паролями могут получить `429`.
Для отправки измерений используется отдельный маршрут
`POST /telemetry` в адаптере. Адаптер передаёт зашифрованные данные на
`POST /telemetry/encrypted` в ядре. Эта цепочка использует ключ телеметрии.

== Пример работы из терминала

Запустите сервисы командой `docker compose up --build -d`. Выполняйте команды
из корня проекта. Примеры ниже используют тестовый email и пароль.
Функция `core` проверяет сертификат локального HTTPS-входа.

[source,bash]
----
core() {
  curl --silent --show-error --fail-with-body --noproxy '*' \
    --cacert certs/ca.crt --resolve core-tls:8443:127.0.0.1 "$@"
}

core https://core-tls:8443/auth/register/start -H 'Content-Type: application/json' \
  -d '{"mail":"sprint5@example.com"}'
----

Сохраните `registration_token` из ответа в переменную `REG_TOKEN`.
Откройте полученную `telegram_url` и нажмите «Старт». Когда
`telegram_confirmed` станет `true`, задайте пароль.

[source,bash]
----
core https://core-tls:8443/auth/register/status -H "Authorization: Bearer $REG_TOKEN"
core https://core-tls:8443/users -H "Authorization: Bearer $REG_TOKEN" \
  -H 'Content-Type: application/json' -d '{"password":"Sprint 5 test password"}'
unset REG_TOKEN
----

Регистрацию выполняют один раз. Для входа сохраните токен из JSON в переменную
текущей оболочки. В примере используется `python3` для разбора ответа.

[source,bash]
----
sprint5_login() {
  local response
  response=$(core https://core-tls:8443/auth/login \
    -H 'Content-Type: application/json' -d "$1") || return
  TOKEN=$(printf '%s\n' "$response" | python3 -c 'import json,sys; print(json.load(sys.stdin)["token"])')
}

sprint5_login '{"mail":"sprint5@example.com","password":"Sprint 5 test password"}'
core https://core-tls:8443/users -H "Authorization: Bearer $TOKEN"
core https://core-tls:8443/devices -H "Authorization: Bearer $TOKEN"
----

После смены пароля прежний токен больше не действует. Войдите с новым паролем,
чтобы получить новый токен. При выходе удалите его из оболочки.

[source,bash]
----
core -X PUT https://core-tls:8443/auth/password \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"current_password":"Sprint 5 test password","new_password":"Sprint 5 updated test password"}' &&
  unset TOKEN

sprint5_login '{"mail":"sprint5@example.com","password":"Sprint 5 updated test password"}'
core -X POST https://core-tls:8443/auth/logout -H "Authorization: Bearer $TOKEN" &&
  unset TOKEN
----

В Postman можно использовать
link:postman/iot2.postman_collection.json[тестовую коллекцию IoT2].
Запрос входа сохраняет токен в переменной коллекции, а следующие запросы
подставляют его в заголовок авторизации.
